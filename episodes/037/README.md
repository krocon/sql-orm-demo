# Folge 037 – Schema Generation vs. Migrationen            (EN: Schema generation vs. migrations)
Video: „Schema Generation vs. Migrationen in 60 Sekunden“ · Serie SQL, ORM & Hibernate

## Worum es geht
Das Feld `name` wird zu `fullName`. Mit `ddl-auto: update` legt Hibernate eine neue, leere Spalte `full_name` an – die alte bleibt, Daten werden nicht übernommen. Richtig: Flyway-Migrationen sind die Quelle der Wahrheit (`RENAME COLUMN`), `ddl-auto: validate` prüft beim Start, und ein von Hibernate generiertes Skript dient höchstens als Startpunkt.

## Ausprobieren
```bash
cd app && ./mvnw test -Dtest='dev.krocon.shop.ep037.**'
cat target/ep037/create.sql          # von Hibernate generiertes DDL (Startpunkt)
# ohne Docker: docker compose up -d, .env laden, DB_URL=jdbc:postgresql://localhost:5433/shop_app setzen
```
Skript selbst erzeugen (Datenbank bleibt unverändert), z. B. in `application.yaml` oder als Test-Property:
```yaml
spring.jpa.properties:
  jakarta.persistence.schema-generation.scripts.action: create
  jakarta.persistence.schema-generation.scripts.create-target: target/create.sql
  hibernate.hbm2ddl.delimiter: ";"
```
Achtung: Hibernate hängt an eine vorhandene Datei an – vorher löschen.

## Dateien
- `app/src/main/resources/application.yaml` – `ddl-auto: validate` + Flyway (Standard-Location `classpath:db/migration`)
- `app/src/main/java/dev/krocon/shop/ep037/Customer.java` – Entity nach der Umbenennung (`fullName` → `full_name`)
- `app/src/main/resources/db/migration/V370__ep037_init.sql` – Ausgangsstand (`name`) mit 2 Kunden
- `app/src/main/resources/db/migration/V371__ep037_rename_name_to_full_name.sql` – `ALTER TABLE … RENAME COLUMN name TO full_name` (Daten bleiben)
- `app/src/test/java/dev/krocon/shop/ep037/DdlAutoTest.java` – startet ein zweites Hibernate gegen ein Hilfsschema mit altem Stand: `update` (Update-Demo) und `validate` (scheitert); Migration behält Daten
- `app/src/test/java/dev/krocon/shop/ep037/GenerateSchemaScriptTest.java` – lässt Hibernate `target/ep037/create.sql` schreiben

## Was du sehen solltest
- `ddl-auto=update` gegen den alten Stand – Hibernate führt aus:
  ```
  alter table if exists ep037_update.ep037_customers alter column email set data type varchar(255)
  alter table if exists ep037_update.ep037_customers add column full_name varchar(255)
  ```
  Spalten danach: `[id, email, name, full_name]`, Daten: `{name=Ana Beispiel, full_name=null}, {name=Ben Muster, full_name=null}`. Nichts gelöscht, nichts umbenannt, nichts übernommen – und nebenbei wurde `email` von `text` auf `varchar(255)` geändert.
- Mit `@Column(nullable = false)` wäre es noch schlimmer: `add column full_name varchar(255) not null` scheitert an den Bestandsdaten (`contains null values`), Hibernate loggt nur eine WARNung und startet trotzdem – ohne Spalte.
- `ddl-auto=validate` gegen den alten Stand: `SchemaManagementException: Schema validation: missing column [full_name] in table [ep037_customers]` (Hilfsschema `ep037_old`).
- Mit Migration V371: Ana heißt weiter „Ana Beispiel“, Spalten `[id, email, full_name]`.
- Generiertes Skript (Ausschnitt) – Typen weichen von den Migrationen ab (`varchar(255)` statt `text`, `generated by default` statt `always`, Check-Constraints für Enums), also prüfen und anpassen, nicht blind übernehmen:
  ```sql
  create table ep037_customers (
      id bigint generated by default as identity,
      email varchar(255) not null,
      full_name varchar(255),
      primary key (id)
  );
  ```
- Default von Spring Boot 4.1 (`HibernateDefaultDdlAutoProvider`): eingebettete DB (H2, HSQLDB, Derby) **ohne** Flyway/Liquibase → `create-drop`, sonst `none`. Die Aussage im Video stimmt.
- Modi: `create`, `create-drop`, `update`, `validate`, `none` (Hibernate kennt zusätzlich `drop`, `create-only`, `truncate`).
